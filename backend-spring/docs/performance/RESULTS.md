# 로컬 성능 비교 — 2026-10-23

## 측정 범위

**실제 Ollama 추론속도나 운영 성능 개선율을 측정한 결과가 아니다.** 현재 클라우드에는 Ollama 실행 파일·GPU 장치·운영 연결 설정이 없고, 기본 localhost 11434/27017/6379도 연결되지 않았다. 기존 Preview 서버는 실제 외부 API와 DB를 대체하므로 운영 측정 대상으로 사용하지 않았다.

비교 대상:

- before: `8c89829` — 번역 전체 잠금, 무제한 상세 준비 대기열.
- previous: `6a98bb2` — 공급자별 잠금, 동일 요청 공유, 상세 준비 대기열 제한.
- after: 측정 시점의 미커밋 작업 트리 — 영속 필드 작업·한국어 완료 조건 추가.

현재 작업과 파일을 덮어쓰지 않고 `/workspace/.bench/anilist`에 별도 복제했다. 세 버전을 순차 실행했다. Java 21.0.8, CPU quota 4코어, 메모리 제한 32GiB. 별도 격리된 전용 벤치마크 머신은 아니며 기존 개발 프로세스가 실행 중이었다. GPU는 없다.

### 캐시·추론 실험

외부 번역은 **200ms sleep을 수행하는 mock**이다. Redis와 DocumentStore도 mock이다. 실제 HTTP·LLM·Redis·MongoDB는 없다. 먼저 캐시 적중 요청 500회로 준비한 뒤, 별도 스레드에서 미적중 번역을 시작하고 추론 진입이 확인되면 다른 문자열의 캐시 적중 요청 시간을 측정했다. 20표본이다. 버전별 외부 mock 호출 20회와 결과 내용을 assertion으로 확인했다.

- 전체 잠금 제거로 캐시 요청이 추론 종료를 기다리지 않는 동작이 확인됐다. 주된 차이는 이미 6a98bb2에서 발생했다.
- 0.169ms와 0.118ms의 차이만으로 최신 변경이 더 빠르다고 단정할 수 없다.
- 미적중 번역은 세 버전 모두 약 203ms다. 모델 계산속도를 개선한 증거가 아니며, 추론 시간은 실험에서 고정했다.
- 전체 상세 API·캐릭터 목록 처리·HTTP 지연·실제 tokens/s를 측정하지 않았다.

### 상세 준비 대기열 포화 실험

150개 작품을 홈의 세 배열에 동일하게 넣어 홈당 450항목을 구성했다. 홈 요청 20회를 반복하고 작업 스레드 2개는 latch로 정지시켜 대기열을 포화시켰다. 새 서비스 인스턴스로 10회 반복했다. 작업이 실제로 2개 실행 중인지 확인한 후 큐 크기를 읽고 실행기를 종료했다. 이 실험은 작업을 끝까지 처리하는 처리량 실험이 아니다.

- 현재 큐는 8,998개에서 100개로 줄어 **대기 작업 개수 98.89% 감소**가 확인됐다. 힙 메모리를 직접 측정한 수치는 아니다.
- 반면 현재 제출 구간은 before 대비 약 **4.76배**, 호출자 CPU 시간은 약 **5.01배**로 증가했다. 개선된 수치로 포장할 수 없다.
- 한국어 판별의 정규식·추가 getter 호출, 중복 검사, 포화 시 반복 제출 거부/예외가 비용 후보다. 각 원인의 비중은 프로파일링하지 않았다.
- 의존성을 Mockito로 대체하고 spy를 사용했으므로 이 CPU 수치에는 테스트 계측 비용이 포함된다. 406.9ms는 홈 20회 전체 구간이지 홈 한 요청의 운영 지연시간이 아니다.
- 따라서 확인된 효과는 **쌓이는 작업 수 제한과 캐시 대기 감소**다. 실제 운영 CPU·메모리·DB 부하 감소율은 아직 알 수 없다.

## 새 필드 작업 기록의 비용

현재 작업 트리만 별도 측정했다. mongo-java-server 메모리 DB를 MongoDB 프로토콜로 접근하고, 번역은 즉시 한국어를 반환하는 mock, 캐시 무효화도 mock이다. 실제 운영 MongoDB나 추론 성능으로 해석하면 안 된다. 20회 원문 변경으로 준비했다.

| 조건 | 표본 | p50 | p95 | TranslationService 호출 |
|---|---:|---:|---:|---:|
| 원문 변경·새 작업 기록·완료 저장 | 50 | 8.669ms | 14.874ms | 50회 |

원문이 같은 필드는 번역 서비스를 재호출하지 않는 것을 확인했다. 기존 번역 캐시도 실제 추론을 줄이던 구조이므로, 이 결과만으로 이전 대비 추론 호출이 100% 감소했다고 말할 수 없다. 새 작업 이력은 DB 읽기·쓰기 비용을 추가한다.

## 재실행

벤치마크 코드는 일반 회귀 테스트에 포함하지 않고 이 폴더에 보관했다. Python 3.12+, Java 21 JDK와 기존 Gradle 의존성이 필요하다. 현재 클라우드의 예:

```bash
cd /workspace/anilist
export JAVA_HOME=/workspace/.tools/jdk-21.0.8+9
export GRADLE_USER_HOME=/workspace/.gradle
python3 backend-spring/docs/performance/run_benchmarks.py
```

스크립트는 새로운 임시 경로에 세 버전을 복제하고, 해당 복사본의 테스트만 실행한다. 출력된 경로에 JSON 원시 표본과 Gradle 로그를 저장한다. 운영 주소를 호출하지 않는다. 이번 실행 원시 값은 `results/`에 저장했다. source-fingerprints.json은 측정 시점 코드 해시이며 후속 수정 후에는 다시 측정해야 한다.

## 실제 서버에서 남은 측정

운영과 유사한 Ollama·MongoDB·Redis가 있는 테스트 환경에서 동일 모델·입력·동시성으로 비교해야 한다. 운영 원본 데이터에 쓰는 부하 실험은 별도 승인과 테스트 데이터가 필요하다.

- Ollama의 cold/warm 호출을 분리하고 total_duration, load_duration, prompt_eval_count/duration, eval_count/duration으로 tokens/s를 계산.
- 직접 Ollama 요청과 애플리케이션 경유 요청을 구분하고 동일 번역 결과·성공률을 확인.
- 캐시 미적중/적중, 원문 변경/동일, 동시 사용자 수별 상세 API p50/p95/p99·처리량·503 비율 확인.
- CPU/GPU·메모리·MongoDB 쿼리 수/시간·Redis hit/miss·큐 크기를 동시에 기록.
- 원문을 빨리 반환하던 버전과 번역 완료까지 요구하는 버전은 응답 정책이 다르므로 지연시간만으로 우열을 판단하지 않음.

다음 최적화 후보는 포화 시 불필요한 재제출을 줄이는 정책, 한국어 판별 정규식 재사용, 준비 작업 등록과 목록 필터 비용 분리다. 이번 요청에서는 측정만 했으며 애플리케이션 로직은 변경하지 않았다.
